## 任务中心「项目加载」性能分析（未改码，仅分析）

Vault 规模：3-任务 下 16 个项目 / 170 个 md 文件。

定位到的瓶颈（调用链：`vault modify` → `refreshFromVaultChange` → `loadProjects` → `buildProjectIncompleteCounts`）：

1. `buildProjectIncompleteCounts`（`src/views/tasks-center/data-loader.ts`）为每个项目调 `listProjectTaskFiles`，
   仅为取「未完成任务数」就把 170 个文件全部 `cachedRead` + 完整解析（4 次 frontmatter 提取 / 全行 checklist 扫描 / 全文 content 驻留内存）。
2. `selectProject → loadTasks` 又对当前选中项目扫一遍，与 1 完全重叠。
3. `buildProjectListSections` 在渲染时重复排序（`loadProjects` 里 `applyProjectSorting` 已排过）。
4. `main.ts` 的 `registerVaultRefreshEvents` 无任何防抖，批量建任务会 N 次全量刷新。
5. 单次 `loadProjects` 触发 4 次 `render()`，每次 `root.empty()` 全量重建两个面板。
6. `Promise.all` 无并发上限；`data.ts` 里 `localeCompare` 未用 Intl.Collator（project-sort.ts 已用）。

优化方向（已向用户提出，待确认）：mtime 级状态缓存 + status-only 轻量解析通道 + modify 防抖与路径定向刷新 +
复用 counts 扫描结果消除重复扫描 + render 合并与 sections 缓存 + 并发限流。

## 基准实测（16 项目 / 155 任务文件，真实 vault）

- 稳态全量重扫：4.8 ms → 0.1 ms（约 33x），磁盘读 155 → 0。
- **冷启动仍需 1319 ms**：155 次磁盘读占绝对大头，解析只占 4.8 ms。缓存解决的是重复刷新，不是首次 IO。
- 后续可选（未做，需用户定）：① 用 `metadataCache.listItems` 做零 IO 快速角标（语义与
  `TASK_LINE_PATTERN` 有差异：注释内任务、空内容任务会被多算，角标可能差 1）；② 渐进渲染——先出项目列表再补角标。
